# 模型自主研发执行方案

日期：2026-09-07。依据：本轮用户明确认可并修正的研发目标、协作方式、工程判断、必要验证和持续反馈共识。

本文是当前中央系统的执行说明与实施交付文档，用户已授权直接落实。最高目标与不可退化边界以[架构与原则](10-架构与原则.md)和[根入口](../AGENTS.md)为准；[75](75-交付质量目标与发展建议.md)保留现状分析，[76](76-重要设计点子与价值.md)保留设计原因。本文明确反馈的最新口径，普通任务不要求全文加载，也不要求执行固定阶段。

## 一、目标和采用能力的依据

> 所有问题，一次就能高效率地完美解决。

一次指用户表达意图后，模型自主完成需要的理解、检索、设计、实现、验证和修正，首次正式交付尽量达到成熟可用的结果。模型自行选择必要动作及顺序，没有规定的内部轮数；内部试验、验证、等待和修复全部计入总成本。

能力是否值得采用，比较有无该能力完成同一问题、达到同等满意结果的总成本：不加能力两轮、1 小时可以解决，加能力一轮却要 2 小时，则不添加。对话轮数、Token、Diff 大小或测试数量都不能单独替代结果与成本判断。

现阶段可以不做需要很重机制却只能提升一点的场景。建设成本与每次使用成本分别考虑：一次投入较大但能持续节省真实任务成本的能力可以评估；实现很轻却让每次任务变慢的能力也应取舍。没有对照证据时，不宣称净收益已经成立。

### 再次评估：方向、价值与实际负担

2026-09-07 复评结论：**保留并落实当前轻量方案，不继续扩建中央机制。** 用户明确的协作偏好足以支持本次指令调整；现有任务证据支持避免旧流程的额外开销，但还不能证明这批新约定已经提高首轮解决率。

| 内容 | 对目标的具体作用 | 实际成本与本阶段决定 |
| --- | --- | --- |
| 一轮意图、最小充分修改、必要确认 | 减少模型反复请用户决策、夹带重构和目标偏移 | 根入口有短指令的读取成本；保留，不为每个任务输出确认表或方案表 |
| 模型按改动选择必要验证 | 用相关检查发现问题，并减少没有新增信息的重复检查 | 复用现有工具，保留自主选择；不建设调度器，不承诺检查后绝对无误 |
| 真实样板与少量条件化工程判断 | 给结构、命名和取舍提供具体依据，减少每次重新选择及风格纠偏 | 读取与维护都有成本；沿用已有资产，只补真实缺口，不批量复制、强制加载 |
| 暂时接受与后续问题、选择性经验整理 | 让后续不足能被发现和修正，避免验收标记阻断反馈 | 主要用于理解反馈；保留，不把它当作提升代码质量的直接证据或新增记账任务 |

本次检查到的实现没有新增运行脚本、依赖、中央状态或固定工具调用；详细资料按需读取，因此主要新增成本是短指令读取与资料维护。历史[模型自主执行决定](decisions/DEC-MODEL-AUTONOMY-EXECUTION-001.md)中的局部修改被流程放大，支持当前继续避免强制生命周期。这个反例不能证明所有新指令都有收益，后续仍按真实任务表现精简。

本方案能更准确表达用户希望模型怎样完成工作；实际输出仍取决于任务事实、所选样板、模型判断和实现。最值得继续完善的是具体项目中有用的事实与样板，本轮不再添加一层管理流程。执行中发现澄清 Contract 原先仅允许存在多种解释时提问，已补上关键事实无法确认的情况，防止少问演变成猜测；同一任务最多 3 次确认保持不变。

## 二、AI 接到任务后如何工作

以下是执行依据，不是必须逐项运行的清单或顺序流程。

| 需要判断的事 | 当前采用的做法 | 何时已足够 |
| --- | --- | --- |
| 用户到底要什么 | 从目标、项目事实和可观察结果理解需求；明确要求与假设分开 | 已有依据足以选择实现，不再为普通细节征求用户决定 |
| 需要看什么 | 自主搜索相关代码、调用方、接口、配置；按需看领域说明和样板 | 能解释问题或实现所需行为，避免为资料完整而全文加载 |
| 怎样改 | 沿用目标项目与适用样板的结构、命名、职责，选择最小充分方案 | 当前目标完整解决，不夹带无关重构、未来占位或公共抽象 |
| 怎样确认 | 根据实际改动选择必要验证，直接针对改变的行为或真实疑点 | 已取得与问题相称的依据，无新输入、新失败或新疑点时停止重复检查 |
| 何时交付 | 模型自主判断，交付成熟结果并说清实际改动、验证和重要限制 | 不为证明“绝对无误”继续增加不相称成本，也不隐藏已知问题 |

模型仍负责真实根因和必要影响范围。最小充分不是最少行数，也不是无条件禁止合理拆分。明显扩大范围时按根入口说明根因、必要性与新增范围；用户明确边界和外部动作授权继续有效。

### 必要沟通最多 3 次

先用项目事实和用户已给出的信息解决疑问。同一任务的必要需求确认最多 3 次，不按子问题重置次数；尽量集中提问、解释影响并给出推荐选择，不重复问已回答事项，也不在一次确认中堆积大量细碎问题。

用户主动提供信息继续用于任务，不视为模型追加追问。确认上限不能变成猜测未知事实或推定授权的理由；仍缺关键事实时，完成可确定部分并一次说明阻碍，不持续追问、不谎称全部完成。外部操作仍须明确授权，缺少授权的动作不执行。

### 验证保持必要、直接、不过度复杂

验证由模型结合本次改动选择，项目已有工具提供事实。系统不新增风险分类器、验证调度器或全量检查套餐。没有输入变化和新疑点时，不重复已通过的验证；遇到失败先处理真实原因，不反复执行同一失败命令来制造进展。

可以为真实需要扩大验证，也可以如实交付未验证边界。类型通过只说明相应类型检查通过，测试通过只说明所测条件下的结果，浏览器检查也不代表所有体验问题消失。人工测试、后续使用反馈与上线授权仍各有其意义。

## 三、工程判断、样板和 Context 如何配合

中央保留跨项目成立的职责与取舍，工程模板保存具体框架、结构、命名和真实样板，业务项目提供当前业务事实。采用参考时核对适用条件，不把模板业务字段、权限码和状态规则原样套进目标项目。

按业务域组织代码、命名清楚、关键事实有来源，都有助于 AI 和人定位及维护。保持现有自主搜索能力；不因需要 Context 而新增中央 Repo Map、全量检索平台或固定加载流程。旧项目不因模板结构更整齐而自动获得整体迁移理由。

工程判断只优先沉淀两类内容：用户明确认可的取舍，以及模型在真实任务中反复判断不好的地方。模型已稳定掌握的常识无需大量重复保存。

一条记录可以用几句话说明：什么情况下、选择了什么、为什么、参考哪里、什么情况下不适用。用户认可的偏好与技术验证事实分开记录；只有真实修复证据才能支持“已验证的故障经验”。

以下仅是表达示意，不是新增的已验证经验：

> 两个表单保存代码看起来相似时，先比较业务规则、错误恢复和状态生命周期。仅形状相似可以继续局部实现；语义稳定一致时才考虑共享。这样可以避免公共封装不断增加特殊参数。参考具体项目实现，并保留其适用边界。

不把“两个重复点”“文件行数”“Diff 阈值”当作自动抽象、拆分或审查的触发器。现有格式与依赖检查可作为项目工具，不能借此接管整项研发。

## 四、暂时接受和后续问题如何理解

**用户没有后续继续相关追问，可以理解为暂时接受；不需要解释用户为什么没有追问。后来再次出现相关问题，继续处理和记录。明确验收也不使问题永久闭环。**

这是对已可见反馈的可修正观察，不是运行状态机。正常收到后续消息、恢复上下文或按需复盘时，就可依据当时可见信息判断；不设置必须等待多久、后台监控、催验收或固定回访。刚交付时不声称已经观察了未来反馈。

| 可见情况 | 如何理解和记录 |
| --- | --- |
| 后续没有相关追问，包括换话题或无后续相关消息 | 截至本次观察暂时接受，不推断原因；不因此要求用户补一句验收 |
| 用户明确表示接受 | 记下明确接受的事实；后续问题仍可追加 |
| 后来再次提出相关问题 | 关联之前目标与改动，核对事实，继续修复或处理；区分原目标缺陷、回归、环境变化和新增要求 |
| 相关历史不可访问，或不能确定消息对应哪个问题 | 说明观察范围不足；不能把没读到反馈当作没有反馈 |

暂时接受可以用于阶段结果观察，但与明确接受分列；不能据此声称已人工测试、没有缺陷、允许上线或用户明确认可了某项工程取舍。后续反馈不受任何“已验收”标记阻止。

日常只在当前对话中处理和保留必要说明，不新增每任务记录文件。需要正式复盘时，使用已有对话、Git 和适当文档，记录当时判断的来源和观察范围；新增反馈修正当前判断，并保留解释前后变化所需的最小事实。

示例：交付“筛选后删除末条数据”的修复后没有相关追问，可暂时接受；之后用户发现返回列表时分页仍不正确，继续核对是否同一原目标的遗漏并修复。此前即使明确说过验收通过，也不关闭这次反馈，更不把它自动当作新需求。

## 五、失败驱动改进如何保持轻量

先解决当前问题，再判断是否有值得保留的改进。没有稳定根因、复用价值或新增有效信息时，可以不产生新资料。

| 已确认的原因 | 最小落点 |
| --- | --- |
| 现有业务事实或说明错误 | 修正原项目说明或事实来源 |
| 模板示例误导了结构或写法 | 修正那个模板样板，不复制一份中央实现 |
| 关键行为容易回归，且有低成本可复用的验证方式 | 保留必要的稳定测试，不同时新增规则和验证包装 |
| 工程取舍被反复判断错 | 在已有合适经验中补条件、原因、案例和边界 |
| 偶发环境问题、用户改目标、根因仍不清楚 | 如实区分，未必形成长期经验 |

项目事实留在项目，模板共性留在模板，跨模板仍成立的经验才考虑中央提升。不能因一次失败自动新建 Skill、检查器或规则，也不能把暂时接受当作案例晋升依据。

随着模型进步，原来补偿弱点的材料若不再节省成本或减少失误，可按事实精简或退役。项目业务规则、接口契约、用户仍认可的风格和样板继续维护。没有固定半年、几年期限，也不新增自动删除任务。

## 六、六个概念如何落在当前系统

Model、Context、Engineering Judgment、Tools、Verification、Learning 是解释能力的六个角度，不要求六个模块，也不组成固定流水线。

| 概念 | 当前承载位置 |
| --- | --- |
| 模型能力 | 现有模型与宿主，由模型自主研发 |
| 相关信息 | 项目代码、配置、领域说明、接口与按需参考资料 |
| 工程判断 | 模板真实样板、项目约定、少量条件化经验 |
| 工具 | 宿主搜索、编辑、Git 和项目已有运行工具 |
| 验证 | 模型根据本次改动选择工具并解释真实结果 |
| 改进 | 当前问题修复，以及必要时更新已有资料或稳定测试 |

## 八、如何判断这次落实是否有效

本次结构验证关注入口仍可定位、已有硬边界与受保护目标仍在、旧中央生命周期没有恢复、资料能互相找到、反馈表述不冲突。这些检查不能证明模型以后一定遵守或交付质量已经提高。

后续有真实任务时，按需比较有无新增约定或样板的同类任务：达到同等结果用了多少总时间、必要确认、用户纠偏与无关改动。观察暂时接受、明确接受和后来发现的问题，并说明观察范围；不通过催验收或隐去后续问题改善指标。

普通任务不为评估多写一套账本，也不强制运行这份方案的每个章节。若某项约定增加的读取、确认或验证成本超过省下的返工，依据实际事实精简该项；需要修改受保护目标或外部动作时继续遵守既有授权边界。
