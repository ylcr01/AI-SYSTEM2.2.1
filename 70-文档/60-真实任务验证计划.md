# 真实任务验证计划

稳定发布前执行 20～30 个真实任务，覆盖 Quick、Standard、Controlled、Local、Structural、Browser/No Browser、项目 Canonical、规格一致性、Decision、整项目底座、Experience Candidate、跨模型 Handoff 和用户退回。

本计划同时是 [`10-架构与原则.md`](10-架构与原则.md) 所定义系统使命的结果验证入口。技术自检证明当前实现满足本次 ChangeSet，不证明中央机制带来长期净收益；机制正式采纳、精简或删除遵循 [`55-系统演进准入.md`](55-系统演进准入.md)。

## 核心指标：Completion Round Distribution

最重要指标是可比问题的一次、二次、三次和四次以上完成占比。一个问题只形成一个样本；首次有效交付计第一轮，每次相关追问、缺陷返回或显式退回增加一轮。没有后续的结果经过默认 7 天静默观察后才计为一次完成。显式验收率保留为辅助强事实，不再要求用户为每次正常交付追加确认。

## 每个真实任务的记录维度

每条记录必须绑定任务发生时的系统版本或 Commit、系统脏状态、Node/平台/架构、逻辑项目身份、任务类型、风险等级和输入周期。模型、推理强度和执行环境只保存宿主显式传入的低敏感标签；未传入时保持 unknown，不猜测。同一仓库的 Local/linked Worktree 以 `gitCommonDir` 归为同一逻辑项目，不得当成多个项目增大样本。版本持续变化时分组统计，不能用当前代码反向假设历史任务当时已经具备某项能力。

### 效率

- 总耗时
- 用户确认次数
- 无效读取文件数
- 真实验证执行次数与耗时
- 失败检查次数
- 阶段耗时（准备、实施、交付、集成、待用户决定）

`completion-rounds-v1` 自动记录问题类型、有效交付、相关后续、完成轮次、显式用户决定和返工。交付尝试与检查执行分开记录：`deliveryAttemptCount` 只表示交付轮次，`verificationExecutionCount` / `verificationExecutionDurationMs` 只累计真实启动的检查及耗时，不用整段交付墙钟时间代替；阶段时间和最小对话闭环事实另行记录。无效读取、目标误解和代码质量仍按真实反馈人工简记，不做模型推断。旧记录缺少检查执行事实时标为 legacy，不反向伪造。

### 准确度

- 是否误解目标
- 是否遗漏 Acceptance
- 是否发生不必要 Scope 扩张

### 代码质量

只用三档记录：明显提升 / 无明显影响 / 明显下降。

抽样检查维度：

- 简洁
- 命名
- 结构
- 性能
- 架构一致
- 可维护性

不做 100 分制或伪精确评分。

### 业务结果

- 完成轮次，以及一次、二次、三次和四次以上分组
- 每个相关后续属于询问、缺陷退回还是自然收口
- 返工次数
- 用户退回原因
- Regression 数量
- 用户手工修正量

验收 `unknown` 只针对已经进入可验收交付、但尚无用户决定的样本。仍在实施、待集成、因预算停止或根本没有完成交付的 Task 不进入验收 unknown 分母。

## 观察项

继续观察：目标误解、Scope、Evidence 缺口、Review 是否改变结论、Contract/Canonical 和整项目底座是否减少返工、规格门禁误报、经验候选复用价值、检查耗时、Handoff 接续和用户退回原因。

问题必须归入目标理解、上下文、实现、验证、控制面、验收或环境之一，并说明依据。单次偶发问题默认只形成观察或项目局部修复；中央机制新增通常要求跨任务、跨项目重复证据，安全、权限、隐私和数据完整性事件除外。

## 机制评估输出

对 Prompt、Context、Contract、Task、Worktree、Evidence、Skill/Agent 或门禁的评估，至少报告：

```text
评估问题与可验证假设
版本、周期、项目和排除项
新版合格、观察中、排除和旧口径样本数
合格已交付样本数与其中未知验收数
完成轮次分布、返工、遗漏/Regression、流程额外耗时和状态债务
真实检查执行次数/耗时与阶段耗时
对模型能力、准确、质量、效率、优雅和清晰的影响
负向成本、反证和不确定性
结论：keep | shrink | remove | observe | experiment
晋升条件、停止条件和回滚
```

只有结果证据支持净正向时才能写成正式优势。缺少 20～30 个新版可比完成样本、可比基线或只完成技术自检时，结论保持 `unknown`、`observe` 或 `experiment`。

## 建议任务集

至少覆盖：

- E01 小 Bug Fix
- E02 普通 Feature
- E03 局部重构
- E04 性能优化
- E05 Web 交互
- E06 Server 事务/状态
- E07 权限任务
- E08 Reference Migration
- E09 Structural Change
- E10 Worktree 并行集成

E10 额外记录任务是否独占 Worktree、集成顺序、目标分支推进前后的提交、冲突与检查失败是否保持目标分支不变，以及成功后任务分支和 Worktree 是否按安全条件清理。

## 记录方式

运行 `node ./40-脚本/task.mjs 评估摘要 --from <日期> --to <日期> [--problem-type <类型>] [--quiet-days 7]` 可只读汇总系统能够确认的完成轮次。人工质量记录继续使用 Markdown / JSON；摘要少于 10 个完成样本时只作方向观察，旧测量版本、问答、只读和不明类型默认退出分母，缺少可比基线时不能宣称机制净收益。不建设 Dashboard 或自动 Agent Benchmark 平台。

## 12 个任务受控对照

上下文、验证或真实性控制策略调整先用 12 个未做过的真实任务做小规模判断：6 个保留调整前设置，6 个启用候选设置，组成 6 组同类型、同风险、规模相近的配对任务，并至少覆盖两个逻辑项目（以 `gitCommonDir` 区分）。模型、推理强度、执行环境、完成轮次口径和项目质量基线保持一致并以 `evaluationContext` 校验；不得重复已做任务制造学习偏差。

每个任务除上述业务指标外，还记录首次压缩发生在第几轮、峰值上下文占比、进入历史的工具输出量、交付次数、首交付后重对齐次数、验证次数与耗时。任一候选任务出现 Scope/Evidence 失真、安全门禁降低、正确行为回退或明显质量下降时立即停止候选组。12 个任务只决定“保留候选、回退或继续观察”：正确性不降低时，峰值上下文或工具输出中至少一项中位数下降 20%，且验证耗时和交付迭代不恶化，才保留候选；稳定结论仍需累计 20～30 个真实任务。

### 本轮真实性修复的专项观察

`DEC-TRUTH-FIRST-CONTROL-SHRINK-001` 在技术交付后的长期净收益状态仍为 `unknown`。上述 12 个受控任务需额外记录：只读误进正式写路由次数、轻量直达终检的有效拦截/误拦截、Quality 失败关闭的可诊断性、导入辅证与直接证明的误判、Browser 熔断/未执行报告、待集成占用冲突、退回旧证明复活、集成预算续期跳态、诊断误报和 Worktree 重复样本。

任一正确行为回退、Scope/Evidence/权限失真、用户已有改动受损或明显质量下降都立即停止候选组。只有 12 个任务显示错路由/错证/状态债务减少且检查执行耗时、交付迭代、用户确认和误拦截未恶化时，才可保留候选；达到 20～30 个可比真实任务之前，不得把技术自检改写为已证明长期优势。

## 规则演进门禁

只有同一能力出现两个以上经真实项目验证且适用条件不同的范式，才扩展中央样板数组。只有重复检查耗时成为可测量瓶颈，才重新评估成功缓存；只有经验数量增长到精确查重和人工复核明显不足，才评估相似度或评分机制。新机制必须由真实退回、返工、误解、质量下降或上下文浪费驱动，不根据文件数、测试数、阶段数或流程完整率自动调整规则。

所有中央机制新增、修改、精简、删除或恢复都在 Decision 或 Change Rationale 中引用 `55-系统演进准入.md` 的核心诉求影响卡。当前实现验证通过只能证明本次变更可交付；后续真实任务达到晋升条件后才能把候选机制提升为正式默认能力。若触发停止条件，应回退、缩小范围或删除，不能用新增检查和状态掩盖净负收益。
