# 真实任务验证计划

稳定发布前执行 20～30 个真实任务，覆盖 Quick、Standard、Controlled、Local、Structural、Browser/No Browser、项目 Canonical、规格一致性、Decision、整项目底座、Experience Candidate、跨模型 Handoff 和用户退回。

## 核心指标：First-pass Acceptance Rate

最重要指标是用户第一次收到交付后、不要求返工直接通过的比例。它是目标理解、实现正确性、代码质量、改动范围与验证有效性的综合结果。

## 每个真实任务的记录维度

### 效率

- 总耗时
- 用户确认次数
- 无效读取文件数
- 验证耗时
- 失败检查次数

V2.3.0 自动记录首次交付、交付次数、验证耗时、显式用户决定、返工和最小对话闭环事实；无效读取、目标误解、首次修复是否真实成功和代码质量判断仍按真实反馈人工简记，不做模型推断。

### 准确度

- 是否误解目标
- 是否遗漏 Acceptance
- 是否发生不必要 Scope 扩张

### 代码质量

只用三档记录：明显提升 / 无明显影响 / 明显下降。

抽样检查维度：

- 简洁
- 命名
- 结构
- 性能
- 架构一致
- 可维护性

不做 100 分制或伪精确评分。

### 业务结果

- 是否首轮验收
- 是否单轮对话闭环，以及首次后续属于相关疑问、缺陷退回还是自然收口
- 返工次数
- 用户退回原因
- Regression 数量
- 用户手工修正量

## 观察项

继续观察：目标误解、Scope、Evidence 缺口、Review 是否改变结论、Contract/Canonical 和整项目底座是否减少返工、规格门禁误报、经验候选复用价值、检查耗时、Handoff 接续和用户退回原因。

## 建议任务集

至少覆盖：

- E01 小 Bug Fix
- E02 普通 Feature
- E03 局部重构
- E04 性能优化
- E05 Web 交互
- E06 Server 事务/状态
- E07 权限任务
- E08 Reference Migration
- E09 Structural Change
- E10 Worktree 并行集成

E10 额外记录任务是否独占 Worktree、集成顺序、目标分支推进前后的提交、冲突与检查失败是否保持目标分支不变，以及成功后任务分支和 Worktree 是否按安全条件清理。

## 记录方式

运行 `node ./40-脚本/task.mjs 评估摘要 --from <日期> --to <日期>` 可只读汇总系统能够确认的结果指标。人工质量记录继续使用 Markdown / JSON；摘要少于 10 个有效样本时只作方向观察，缺少可比基线时不能宣称机制净收益。不建设 Dashboard 或自动 Agent Benchmark 平台。

## 12 个任务受控对照

上下文或验证策略调整先用 12 个未做过的真实任务做小规模判断：6 个保留调整前设置，6 个启用候选设置，组成 6 组同类型、同风险、规模相近的配对任务，并至少覆盖两个项目。模型、`xhigh` 推理强度、用户验收口径和项目质量基线保持一致；不得用已经做过的同一任务重复执行制造学习偏差。

每个任务除上述业务指标外，还记录首次压缩发生在第几轮、峰值上下文占比、进入历史的工具输出量、交付次数、首交付后重对齐次数、验证次数与耗时。任一候选任务出现 Scope/Evidence 失真、安全门禁降低、正确行为回退或明显质量下降时立即停止候选组。12 个任务只决定“保留候选、回退或继续观察”：正确性不降低时，峰值上下文或工具输出中至少一项中位数下降 20%，且验证耗时和交付迭代不恶化，才保留候选；稳定结论仍需累计 20～30 个真实任务。

## 规则演进门禁

只有同一能力出现两个以上经真实项目验证且适用条件不同的范式，才扩展中央样板数组。只有重复检查耗时成为可测量瓶颈，才重新评估成功缓存；只有经验数量增长到精确查重和人工复核明显不足，才评估相似度或评分机制。新机制必须由真实退回、返工、误解、质量下降或上下文浪费驱动，不根据文件数、测试数、阶段数或流程完整率自动调整规则。
