# 可信门禁

正式进入 `waiting_acceptance` 必须同时满足：

- 显式正式 Task 的 Baseline 来自任务专属 linked Worktree；Local/主工作区准备正式 Task 以 `WORKTREE_REQUIRED` 失败关闭。普通修改不调用 `准备`，直接在满足事实预检的当前工作区实施；
- 项目和 Git Root 有效；
- 显式 Quality 配置是可解析的受支持 shape，且配置本身、Contract、Canonical 和其他 Context 读取项都是各自授权根内实际可读文件；显式无效配置不得回退为无配置；
- Git Baseline、工作树状态、ChangeSet 和集成状态均能被真实确认；Git 命令失败必须停止，不能解释为空状态；
- 正式 Task 或用户明确限定的 Scope 在 Git Root 内；普通修改以实际 ChangeSet 作为结果范围；
- 用户已有改动未被未授权触及；
- ChangeSet 当前有效；
- Evidence Schema、Payload Hash、Acceptance 和 Covers 有效；
- 导入的 Evidence 或外部结果只记为辅证，不能直接闭合 Acceptance。`documentation`、`contract` 或 `visual` 的直接证明必须来自系统执行的用例，并绑定 Git Root 内存在的 artifact 及其当前 SHA-256；产物越界、不存在、不是文件或哈希变化均失败关闭；
- 通用项目检查只证明自己声明的全局 Covers，不能按 Covers 猜测并自动证明 Acceptance；Acceptance 只有被明确列出的检查才算满足；
- 新 Task Check 必须使用 Schema 2，只能声明受控 Runner 和 cases，不能携带任意命令、参数或副作用声明；每个 case 显式绑定 Acceptance、Cover、测试文件与精确用例名。只有目标用例实际命中预期数量、全部执行通过且没有 skip/todo 时才能形成 Acceptance Evidence；零命中、错选、失败、skip/todo 或用例事件无法解析均失败关闭；
- 每个用例只能形成一条绑定自身 `Acceptance × Cover` 的 Evidence；同一 Check 内不同 case 的 Acceptance 与 Cover 不得聚合成交叉组合。实际执行计划保存为 Check Manifest，固化 cases、Runner/结果协议版本与测试文件哈希，后续验证重放同一计划；Schema 1 的退出码协议仅可重放不绑定 Acceptance 的全局检查，显式绑定 Acceptance 的旧 Manifest 或 Evidence 必须失败关闭并重新交付；
- Task Check 必须在命令执行前完整映射当前缺失的 `Acceptance × Cover`；不完整时停止在 `missing-acceptance-checks`，不得先运行不能闭合验收的通用检查。完整后，通用检查只补真实 ChangeSet 尚未覆盖的 Required Covers；整批失败时不得保留批内较早检查的部分成功 Evidence；
- Browser Check 只接受用例级 `node-test` Runner，一个 Check 一条 flow，最多 4 条，单条最多 15 秒、Browser 整批最多 120 秒、包含前置检查的外层最多 180 秒；首个失败或超时立即熔断，结果必须分别报告 completed、failed、timedOut 和 blocked。当前同步 Runner 无法在子进程期间执行 30 秒心跳和无有效输出终止，必须将该缺口结构化报告为 `unimplemented`，不得伪装已执行；
- Required Covers 和 Acceptance 均被证明；
- 无当前仍成立的人工 Blocker 和 Blocking Review Finding；Handoff 失效、已有改动重叠等派生原因每次按当前事实重新计算，不作为永久 Blocker；
- 用户/项目显式要求的 Review 已满足；
- handoff-required 任务存在新鲜 Handoff。
- linked/detached worktree 任务已经形成独立 `resultCommit`，且没有未提交的任务改动；
- 需要集成的任务已经确认：merge 后原 `resultCommit` 可达，或 cherry-pick 后全部任务补丁存在等价提交；用户验收时声明目标分支的当前 HEAD 必须与最近一次集成确认或重验绑定的 `targetCommit` 完全一致。

工程交付通过上述校验后进入 `waiting_acceptance`，对外只说明“本轮已交付”，不要求用户为结束当前对话形式化确认。每次交付返回精确 continuation；所有不同 `observationId` 的相关询问保持该状态并增加完成轮次，范围扩展、非正式肯定或独立话题推进可以进入 `closed`。缺陷或用户退回必须先持久化退回事实、使上轮 Evidence、Review、Handoff、Rationale 和 Check Manifest 失效并提升输入周期；未集成任务进入 `needs_rework`，已集成任务先进入 `blocked`，再安全恢复专属返工 Worktree。恢复成功后进入 `verifying`；恢复失败保持 `blocked`、保留诊断并允许用 `恢复` 重试。恢复以最新目标 HEAD 为返工基线；保留的源 Worktree 若含脏内容不得 reset 或覆盖。相同 ChangeSet 且未重新对齐时不得再交付。相关询问等非退回回写不重新执行工程检查，也不改变 Evidence。

显式验收是可选强事实，执行前仍重新校验；`accepted` 只能通过用户验收事件产生，`closed` 只能由封闭的对话收口事件产生。完成统计不从 `accepted` 推断，而使用当前测量版本、有效交付、相关后续和静默观察事实。

所有正式写 Task 在 Evidence 和 Review 满足后先进入 `ready_to_integrate`。该状态仍属于写作占用态，源 Worktree 不得被其他 Task 占用；系统为其创建 `refs/ai/pending/<taskId>`，防止 detached commit 因 Worktree 清理而丢失。低风险的正式 Task 由单一集成者在专属临时 Worktree 中把任务提交应用到最新目标 HEAD，重放固化的 Check Manifest，只在目标 HEAD 未变化时 fast-forward。成功进入 `waiting_acceptance` 后才释放占用，并在精确 HEAD/干净约束下清理 pending ref、集成 Worktree、源 Worktree 和任务分支。`ephemeral` 轻量直达不进入本流程。

目标 checkout 脏、冲突未解决或未提交、检查失败、目标 HEAD 变化，以及 Controlled/Structural、规格待决策或存在残余风险时必须停止，目标分支保持不变并保留可恢复结果。冲突解决并提交后可重跑同一 `集成` 命令；风险任务需要明确授权和原因。`集成 --confirm-only` 继续支持外部先完成 merge/cherry-pick 的兼容流程。首次集成与后续重验采用同一检查证据规则。

`WORKTREE_REQUIRED` 与 `WORKTREE_CONFLICT` 只服务显式正式 Task 或真实工作树占用，不由意图关键词、目录名、文件类型、Controlled/Structural 标签或模型自行扩大的 Scope 自动触发。普通修改在预检确认当前工作区干净、可用、分支明确且没有已知并发写入后，由模型直接实施、验证并展示 Git Diff；脏、占用、并发或状态不确定时进入 Worktree保护已有改动。用户明确要求提交并记录轻量结果时，可选运行无状态终检：HEAD、branch/detached、`gitRoot`、`gitCommonDir` 和占用变化必须拒绝；只有用户明确限定 Scope 时才校验越界，否则范围从真实 ChangeSet 得出。任何路径都不得自动 Push。

目标分支 HEAD 在集成确认后变化时，直接验收必须失败。模型在干净且 HEAD 与目标分支一致的目标工作区运行 `task.mjs 重验集成`，系统重新执行当前 Task 必要检查，生成绑定新 HEAD 的 Integration Evidence 后才恢复验收资格。

验证预算耗尽后 Task 不得通过无限开关继续。取得用户对追加预算的明确授权后，由模型运行 `task.mjs 继续验证 --additional-budget-ms <毫秒> --reason <原因>`；若耗尽发生在集成检查，Task 保持 `ready_to_integrate`，续期只恢复 integration ready，不转成 `needs_rework` 或 `waiting_acceptance`、不重算 ChangeSet。追加不放宽单项检查、Browser 或外层进程硬超时。

`task.mjs 诊断状态` 始终只读并分开报告 `storageIntegrity` 和 `acceptanceEligibility`。只有存储完整时才重验待验收 Task 的当前资格；存储完整不代表验收资格成立，两者不得合并为一个 `ok`。

新 Task 的系统版本/Commit/脏状态和 Node/平台/架构由系统当时捕获；模型、推理强度和执行环境只接受 `准备` 时宿主显式传入的低敏感标签。缺少标签保持 null，不猜测、不抓取完整环境变量或密钥。

`forcedMode` 只允许把真实分类向上加强。文本参数不能声明“输入已变化”来清除失败；只有真实 ChangeSet 变化或正式重新对齐会形成新的验证依据。
