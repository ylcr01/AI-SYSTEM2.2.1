# 可信门禁

正式进入 `waiting_acceptance` 必须同时满足：

- 项目和 Git Root 有效；
- Git Baseline、工作树状态、ChangeSet 和集成状态均能被真实确认；Git 命令失败必须停止，不能解释为空状态；
- Scope 在 Git Root 内；
- 用户已有改动未被未授权触及；
- ChangeSet 当前有效；
- Evidence Schema、Payload Hash、Acceptance 和 Covers 有效；
- 通用项目检查只证明自己声明的全局 Covers，不能按 Covers 猜测并自动证明 Acceptance；Acceptance 只有被明确列出的检查才算满足；
- 新 Task Check 必须使用 Schema 2，只能声明受控 Runner 和 cases，不能携带任意命令、参数或副作用声明；每个 case 显式绑定 Acceptance、Cover、测试文件与精确用例名。只有目标用例实际命中预期数量、全部执行通过且没有 skip/todo 时才能形成 Acceptance Evidence；零命中、错选、失败、skip/todo 或用例事件无法解析均失败关闭；
- 每个用例只能形成一条绑定自身 `Acceptance × Cover` 的 Evidence；同一 Check 内不同 case 的 Acceptance 与 Cover 不得聚合成交叉组合。实际执行计划保存为 Check Manifest，固化 cases、Runner/结果协议版本与测试文件哈希，后续验证重放同一计划；Schema 1 的退出码协议仅可重放不绑定 Acceptance 的全局检查，显式绑定 Acceptance 的旧 Manifest 或 Evidence 必须失败关闭并重新交付；
- Task Check 必须在命令执行前完整映射当前缺失的 `Acceptance × Cover`；不完整时停止在 `missing-acceptance-checks`，不得先运行不能闭合验收的通用检查。完整后，通用检查只补真实 ChangeSet 尚未覆盖的 Required Covers；整批失败时不得保留批内较早检查的部分成功 Evidence；
- Required Covers 和 Acceptance 均被证明；
- 无当前仍成立的人工 Blocker 和 Blocking Review Finding；Handoff 失效、已有改动重叠等派生原因每次按当前事实重新计算，不作为永久 Blocker；
- 用户/项目显式要求的 Review 已满足；
- handoff-required 任务存在新鲜 Handoff。
- linked/detached worktree 任务已经形成独立 `resultCommit`，且没有未提交的任务改动；
- 需要集成的任务已经确认：merge 后原 `resultCommit` 可达，或 cherry-pick 后全部任务补丁存在等价提交；用户验收时声明目标分支的当前 HEAD 必须与最近一次集成确认或重验绑定的 `targetCommit` 完全一致。

用户验收前重新执行上述校验。`accepted` 只能通过用户验收事件产生。

并行任务在 Evidence 和 Review 满足后先进入 `ready_to_integrate`。系统为其创建 `refs/ai/pending/<taskId>`，防止 detached commit 因 worktree 清理而丢失。单一集成者完成 cherry-pick 或 merge 后执行 `task.mjs 集成`；系统先在干净的目标 HEAD 重放交付时固化的 Check Manifest，通过后才清理 pending ref 并进入 `waiting_acceptance`。首次确认与后续重验采用同一规则。

目标分支 HEAD 在集成确认后变化时，直接验收必须失败。用户在干净且 HEAD 与目标分支一致的目标工作区运行 `task.mjs 重验集成`，系统重新执行当前 Task 必要检查，生成绑定新 HEAD 的 Integration Evidence 后才恢复验收资格。

验证预算耗尽后 Task 不得通过无限开关继续。用户必须运行 `task.mjs 继续验证 --additional-budget-ms <毫秒> --reason <原因>`，显式追加有限预算；追加不会放宽单项检查、浏览器冒烟或外层进程的硬超时。

`forcedMode` 只允许把真实分类向上加强。文本参数不能声明“输入已变化”来清除失败；只有真实 ChangeSet 变化或正式重新对齐会形成新的验证依据。
