# 目标对齐与漂移控制（V2.2.2 能力说明）

> 状态：阶段 1（写前对齐）、阶段 2（交付映射与风险升级）、阶段 3（重新对齐命令）已落地；阶段 4（数据驱动调优）与阶段 0（基线标注）按真实数据另行开展。

## 解决的问题

- A 需求理解错误：模型围绕第一个合理解释直接写代码。
- B 执行中渐进漂移：多次“顺手优化”累积替代原目标。
- C 复杂方案未确认就执行。
- D Scope、非目标和保护行为漂移。

不解决：模型编码能力、算法或框架知识错误、测试覆盖不足、环境故障、需求真实变化。

## 核心原则

固定“要做成什么、什么不能破坏、怎样算完成”，不固定“必须怎么写代码”。机器只判断可确定事实，模型负责语义，用户只决定实质业务事项。

## 工作流与执行模式

1. 普通清晰任务：build-context 只读理解 → 输出 3～5 行目标卡 → direct → 准备 Task → 自主实现 → 交付映射 + Evidence → waiting_acceptance。
2. 复杂或实质歧义：先给 Goal/Outcome/Protected Behaviors/Acceptance 与方案取舍，停止写代码，用户确认或明确委托后执行（confirmed / delegated）。
3. 根因未知：只读探索定位后再决定模式，不创建写 Task。

- `direct`：目标清楚、局部、无不同业务结果的替代解释；Controlled/Structural 禁止 direct。
- `confirmed`：用户确认 Goal、最终效果或关键方案，必须记录 `decisionNote`。
- `delegated`：仅当用户明确授权，必须记录 `delegatedTopics` 与边界，不能绕过 Scope、外部写入与不可逆动作门禁。

## 对齐文件与 Task 存储

`准备 --alignment-file <json>` 读取轻量 JSON：`originalRequest / goal / expectedOutcomes / protectedBehaviors / acceptance / confirmedDecisions / nonGoals / assumptions / alignment{mode,reasonCodes,decisionNote,delegatedTopics}`。

存入现有 Task 的 `goal` 字段（不建第二套 Anchor），扩展为语义基线并计算 SHA-256 基线指纹；指纹只证明基线文本未被静默改写，不证明理解正确或代码未漂移。Protected Behaviors 自动转为 Acceptance 并标记 `source`，无 Evidence 的保护行为不能视为已保持。Quick 旧参数自动合成最小 direct；旧 Task 读取为 legacy，不回写、不强制迁移。

## 交付映射与风险升级

- 交付时 Standard/Controlled 对齐任务必须提供 `--rationale-file`，每个 ChangeSet 文件至少映射到一条 Acceptance 或特殊标记 `GOAL`；未知文件、未知 Acceptance、空 reason、旧指纹被机器拒绝。
- 校验失败时：Standard 保持 `verifying`；Controlled 未映射文件进入 `needs_rework` 并带 blocker。Quick 不要求映射。
- direct 任务实际 ChangeSet 被重新分类为受控、或命中 HARD_RISK_PATTERNS 时，不得进入等待验收：进入 `needs_rework`，blocker 为 `alignment-risk-escalation`，并在 `goal.alignment.events` 记录实质事件。
- Review Package 增加对齐摘要（模式、修订、指纹、保护行为、已确认决定、实质事件）与 Change Rationale，不改变现有 Review 决策结构。

## 事件触发重对齐

不做每轮自检。只有 Goal、Outcome、Acceptance、Protected Behavior、已确认决定、Scope 或风险发生实质变化时才暂停重新对齐；低风险假设被推翻只影响内部实现时模型自主调整并记录实质事件。

## 重新对齐命令

`task.mjs 重新对齐 --task-id <id> --alignment-file <json> --reason <text>`：

- 允许改变 Goal、Outcome、Protected Behavior、Acceptance、Decision、Non-goal、Assumption 与执行模式；新模式只能是 confirmed 或 delegated，必须记录 decisionNote 与原因。
- 不允许改变 Scope、外部动作授权、集成目标与用户已有改动授权；这类变化应保存或取消当前任务并以新授权重新准备。
- 行为：`alignment.revision + 1`，记录新旧基线指纹与原因，清空旧 Evidence、Review、Review Package、Handoff 与 Change Rationale，`verification.inputCycle + 1`，状态回到 `implementing`；现有代码改动不自动删除，交付时按新目标重新映射和验证。
- 已 `ready_to_integrate` 或已结束的任务应创建新 Task，不在原任务上重对齐。

## 效果口径

过程指标可承诺：受控未确认直接准备、Scope 静默扩大、direct 风险升级后仍直接交付、未映射文件仍交付均应为 0。理解准确率、A～D 退回下降比例只按真实任务统计，不在设计阶段提前承诺。
