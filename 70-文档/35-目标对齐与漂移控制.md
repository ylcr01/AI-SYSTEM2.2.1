# 目标对齐与漂移控制（V2.2.2 能力说明）

> 状态：阶段 1（写前对齐）、阶段 2（交付映射与风险升级）、阶段 3（重新对齐命令）已落地；阶段 4（数据驱动调优）与阶段 0（基线标注）按真实数据另行开展。

业务规则以 [`20-能力模块/clarify-requirements/CONTRACT.md`](../20-能力模块/clarify-requirements/CONTRACT.md) 为准；本文只说明当前实现，不再重复完整协议。

## 目标与边界

- 固定“要做成什么、什么不能破坏、怎样算完成”，不固定代码写法。
- 防止第一个合理解释直接落地、执行中渐进漂移、复杂方案未确认和 Scope/保护行为漂移。
- 不处理模型编码能力、框架知识、测试覆盖、环境故障或需求真实变化。
- 机器只判断可确定事实，模型负责语义，用户只决定实质业务事项。

## 实现概览

1. 清晰局部任务输出简短目标卡后直接准备；复杂歧义先确认或取得明确委托；根因未知时先只读探索。
2. `准备 --goal-card-file <json>` 读取 Goal Card，旧 `--alignment-file` 仅作兼容别名。Quick 旧参数仍自动合成最小 direct。
3. Goal Card 存入 Task 的 `goal` 字段并计算基线指纹；Protected Behaviors 自动转为 Acceptance，没有 Evidence 时不能视为已保持。
4. 交付映射把 ChangeSet 文件绑定到 Goal 或具体 Acceptance；未知文件、未知验收项、空原因和旧指纹会被拒绝。
5. direct 任务在实际变更升级为受控或命中高风险模式时进入重新对齐，不直接进入待验收。
6. Review Package 仅在显式要求审查时附带目标摘要与 Change Rationale。

Goal Card 的最小字段为：`originalRequest / goal / expectedOutcomes / protectedBehaviors / acceptance / confirmedDecisions / nonGoals / assumptions / alignment{mode,reasonCodes,decisionNote,delegatedTopics}`。

## 重新对齐

`task.mjs 重新对齐 --task-id <id> --goal-card-file <json> --reason <text>` 只接受 confirmed 或 delegated，并记录原因与修订指纹。它可以更新目标、Outcome、保护行为、Acceptance、Decision、Non-goal 和低风险假设，但不能改变 Scope、外部授权、集成目标或用户已有改动授权。

重新对齐会清空旧 Evidence、Review、Handoff 和 Change Rationale，增加输入周期并回到实现态；已准备集成或已结束的 Task 应创建新任务。

## 效果口径

受控任务未确认直接准备、Scope 静默扩大、direct 风险升级后仍直接交付、未映射文件仍交付应保持为 0。理解准确率和退回变化只按真实任务统计，不在设计阶段提前承诺。
