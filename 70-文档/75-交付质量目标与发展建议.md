# 交付质量目标与发展建议

评估日期：2026-09-07。中央版本：V3.0.0，评估起点提交 `5f6661f`。

本文记录用户本次诉求及基于当前仓库的分析，并按同日后续澄清更新：最终目标是所有问题一次、高效率地完美解决，重投入而微收益的场景可以现阶段不做。本文不新增默认流程、自动加载、检查或授权要求；[架构与原则](10-架构与原则.md)中的最高目标、使命、六项诉求与边界保持权威。

重要设计点子单独保存在[重要设计点子与价值](76-重要设计点子与价值.md)，避免只留下结论而丢失设计原因。

用户随后确认的执行方式及本次落地见[模型自主研发执行方案](77-模型自主研发执行方案.md)：必要需求确认最多 3 次，模型按改动选择必要验证并避免冗余复杂流程；没有后续相关追问可暂时接受，后来出现问题继续记录，明确验收也不构成永久闭环。

## 一、用户真正希望得到什么

用户明确的最终目标是：**所有问题，一次就能高效率地完美解决。** 后续系统所有功能都围绕这一目标建设。模型理解准确、事实可靠、功能和整体效果符合预期、代码优雅并符合工程习惯，以及减少用户纠偏、返工、越界修改和无关重构，都是对这一目标的展开。

**高效率是与一次解决、完美交付共同成立的核心要求。** 首轮满意交付率、返工、范围和总耗时用于观察距离目标还有多远；这些阶段指标不替代或缩小最终目标。

用户进一步明确，能力的采用依据是有无该能力的对照收益：完成同一问题、达到同等合格结果时，不加能力两轮对话、1 小时能解决，加能力一轮对话却要 2 小时，则不添加。一次解决是最终目标，但阶段能力不能为了减少轮次而增加总成本；可以保留当前更高效的两轮方案。这个例子说明取舍逻辑，不是本次测得的系统性能数据。

“首轮满意交付”包含模型自主查证、实现、运行、观察和修正后的首次正式交付。它不要求第一遍生成的代码就正确，也不要求模型省掉必要的内部验证。需要减少的是用户反复补充常识、纠正理解、指出遗漏和要求返工的次数。

可操作的结果口径是“首次交付完整满足用户目标与质量预期，没有因误解、遗漏、缺陷、效果或工程风格问题发生实质返工，同时总成本与任务规模相称”。探索性需求可以有必要澄清，目标在实施后变化也应与模型失误分开。内部验证与修正同样计入时间，不能用长时间内部反复来美化一次交付指标。

最终目标与阶段投入分开处理：某项能力相较不添加的方案只减少少量错误或对话，却增加更多执行、沟通与等待成本时，可以现阶段不做。重点比较完整问题的总成本，而非单看系统实现轻重、一次耗时或对话轮次。一次建设投入较大但能为适用任务持续节省相称成本的能力，可以进一步考虑。暂缓不等于已解决，也不要求其他普通任务为该场景承担额外流程。

| 用户的白话诉求 | 可用于判断结果的具体含义 |
| --- | --- |
| 输出更准确，少幻觉 | API、字段、权限、版本和代码行为有当前事实依据；假设与未知不伪装成事实 |
| 少反复沟通 | 从现有代码、项目约定和已认可案例中主动补齐信息，只询问真正改变业务结果的歧义 |
| 功能做出来，整体也满意 | 主路径、状态衔接、信息层级、视觉密度、反馈和恢复体验符合预期 |
| 不扩大范围、不顺手重构 | 修改服务于当前目标；不夹带无关改名、格式整理、公共抽象和架构迁移 |
| 最小修改、代码优雅 | 用完整解决问题所需的最小充分方案，职责清晰、复用现有能力，兼顾维护成本 |
| 风格、结构、命名统一 | 在同一项目及其选定模板体系内稳定一致，不由每轮模型重新发明 |
| 效率高 | 计算从提出需求到接受结果的总耗时，包含读取、编码、验证、等待、纠偏和返工 |

最小修改不等于最少行数：为修复根因增加一个必要分支或保护关键行为的测试，可能比一行掩盖报错更小、更可靠。代码优雅也不等于层次更多；是否拆分取决于当前职责和真实变化原因。

### 模板体系的方向是对的

中央通用样板负责描述跨项目成立的职责和做法，项目模板负责具体框架、目录、文件名、代码写法与真实工程示例，业务项目负责当前目标和业务事实。这种分工符合用户希望通过样板统一输出的目的。

中央 Web 样板写“统一职责而非所有文件名”，与用户要求统一命名并不必然冲突：跨框架资料需要保持通用，选定的项目模板则可以明确使用 `index.vue`、`data.ts`、`api/`、`modules/` 等约定。统一应落到选定的工程体系，不能借此批量改造其他项目。

目前 Web 模板的 `docs/开发指南/新增业务模块.md` 已把这件事做得较具体：既提供最小结构，也链接角色、用户、菜单、部门、品牌等真实实现，并说明请求命名、提交锁定和纯模型拆分。下一步应完善和使用这些资产，而非再复制一套中央代码样板。

### 还有两处具体衔接问题

1. **项目到样板的使用关系尚未在可检查的业务项目上闭合。** 注册表支持 `templateId` 绑定，但当前登记项目未绑定且路径不可访问。这不是要求所有老项目强制绑定；应先找到真实使用中的目标项目，核对它适用的模板及自身约定，再建立准确入口。
2. **App 的部分知识入口仍保留旧口径。** `.ai/README.md` 写有按关键词命中文件读取的说明，`.ai/manifest.json` 保留 `routes/keywords`，与中央 V3 的模型自主选材原则不一致。本次只确认文档与配置残留，没有证据证明运行时仍执行自动路由。后续宜局部核对并统一表述，保留有用的项目验证命令。

## 三、系统有没有走偏

**判断：历史上中央流程曾偏重，V3 已明确纠正；当前总体方向符合目标，但具体质量参照与真实结果反馈还需要继续做实。**

[模型自主执行决定](decisions/DEC-MODEL-AUTONOMY-EXECUTION-001.md)记录了一次真实 POC：约十行的局部修改被升级成正式 Task，并引入 Scope 重建、两个 Worktree、重复验证和集成清理。记录中一次运行约 9 分钟后取消，另一次准备到集成约 2 分 32 秒，正式检查仅 397 毫秒。这支持“旧机制在该任务上成本不相称”的结论，不能外推为所有隔离或验证都无价值。

另一份本机历史记录 `task-20260821022614794-55f3317c` 中，用户因 Gas Sensor 表格整体偏小、需要约放大两倍而退回交付。它说明视觉比例属于满意度的一部分；记录本身不足以判定首次提示是否已明确尺寸，也不能单独证明模型遗漏了已知要求。

因此，有两种后续偏离值得避免：

- 把提高准确率重新变成更多通用规则、强制清单、默认 Agent、自动路由和任务状态。具体问题应先在项目代码、事实和样板中解决。
- 把系统建设停留在安全边界与抽象原则。边界解决权限、范围和真实性问题；高质量样板、领域事实和效果参照还要让模型知道什么结果是合适的。

当前材料能够支持架构方向判断，不能支持“V3 已明显提高准确率”“模板已显著减少返工”等效果结论。模板标记 `stable`、声明工程验收、存在测试，都不能替代本次真实运行和后续用户验收统计。

## 四、建议的后续投入顺序

### 优先一：把已有模板中的优秀实现选准、讲清、用起来

先围绕实际常做的任务完善少量代表性样板，例如普通列表与编辑、复杂配置、移动端分页与恢复、服务端业务更新。优先选择已有源码，不新建一批演示工程。

每个样板只补充模型确实需要的信息：适用问题、真实路径、关键取舍、哪些约定值得沿用、哪些业务字段不可照搬，以及已有验证与未验证边界。具体命名交给模板文档和现有格式化/Lint 配置共同表达。

判断价值时看后续功能是否更自然地沿用结构、命名和状态处理，以及用户是否减少了风格纠偏。即使样板存在，如果没有被使用或复制后引入更多无关文件，也不能算改进。

### 优先二：补上“整体效果满意”的参照

工程样板之外，为最常用页面保存少量经用户认可的成品参照：页面或交互入口、适用屏幕与数据密度、关键视觉取舍、主要状态与恢复行为。可用已有页面和说明表达，必要时保留经过选择的参考图，不存整轮运行截图。

例如“表单提交失败”应描述用户仍能看到原输入、错误可理解、可以再次提交；“表格清晰”应关联真实屏幕、列密度、字号和缩放场景。这样模型能够针对用户结果自行检查，减少把“能打开”“构建通过”当作满意交付。

已有组件和主题变量是基础，但它们不能独自决定信息层级、页面节奏和完整操作感受。对于审美差异较大的新需求，一次关键澄清可能比错误方向上的完整实现更高效。

### 优先三：完善真实项目的事实入口

从一个正在使用的项目开始，确认仓库身份、适用模板、相邻样板、领域术语、接口来源、关键业务规则和实际验证命令。优先补已有项目文档的短入口，不创建中央自动上下文系统。

模型使用参考的建议顺序是：本次明确目标与约束 → 项目现行约定和相关事实 → 适用模板的真实样板 → 中央通用范式。发现模板、文档和代码冲突时查证原因；现存代码不自动代表用户最希望推广的写法。

版本相关事实以项目依赖和当前接口实现为依据，无法从本地确认时再查适用版本的官方资料。功能相似不等于接口、权限码、平台行为或数据规则相同。

### 优先四：把减少返工变成可观察结果

建议从下一小批同类真实任务中做一次人工抽样复盘，先固定项目、任务类型、系统与模型版本，并记录样板版本。利用现有对话、Git 和用户反馈即可，无需恢复每任务账本。

| 观察项 | 口径 |
| --- | --- |
| 首次交付后的接受情况 | 截至可见反馈没有后续相关追问可暂时接受，与明确接受分列；之后有相关问题继续记录并修正当前判断 |
| 纠偏与返工 | 将实施前必要澄清、用户改目标、因理解/实现/效果/风格产生的纠偏分开 |
| 范围与回归 | 是否有与目标无关的重构、遗漏既有行为或新增缺陷，而非只统计文件数 |
| 总成本 | 提出需求到接受结果的总耗时；可取得时再区分模型工作、流程与等待时间 |
| 有无能力的对照 | 在同类问题和同等结果要求下，比较不用该能力的全部轮次总成本与使用后的总成本；轮次减少但总成本增加，不据此采用 |
| 事实真实性 | 是否编造接口、误用过期资料，或将未运行、未验收表述为已验证、已通过 |

报告所观察任务、反馈来源和观察范围，分列暂时接受、明确接受以及后来出现的相关问题。暂时接受包括没有继续相关追问的情况，不需要推断用户沉默或换话题的原因；相关历史不可访问、无法判断问题归属时才说明观察不足。需要计算阶段接受或未再纠正的比例时，明确分母和观察截止点，分列暂时与明确接受；后续反馈继续修正结果，不能把该比例称为永久解决率或人工测试通过率。普通任务无需为此增加记录表或催验收。

先用少量可比较任务检验方向；是否足以讨论稳定性取决于任务差异和观察到的结果，不设必须凑满的任务数，也不为了评估制造额外任务。模板参与了成功任务不能证明它导致成功；可在相近任务中比较“现有入口”与“现有入口加选定样板参照”，不同时更换模型、模板和验证方式。对照中的全部纠偏轮次和等待都计入总成本，不能以一轮优于两轮预先判定结果；没有可比较对照时，只能记录待验证判断。

若样板没有减少纠偏，先检查是否找到、是否适配、是否描述了真正影响结果的维度；若持续增加上下文与维护成本，应缩小或停止扩展。

| 验证的结果相关性与执行成本 | 模板已有测试、构建与行为验证工具；技术通过不能证明整体满意 | 模型按本次改动选择必要验证，复用已有工具，避免冗余复杂流程；不固定全量验证，结果如实表达 |

### 可以现阶段不做：高成本、微收益或尚无需要的建设

| 暂缓项 | 为什么暂缓 | 什么时候值得再看 |
| --- | --- | --- |
| 中央任务状态机、自动路由、通用评分和默认多 Agent 评审 | 现有证据未显示可降低总成本，旧生命周期已有反例 | 具体重复问题有事实支持，且模型、宿主和项目工具都无法低成本解决时；仍需符合现有硬边界 |
| 为少见场景预建完整能力、平台矩阵或全量案例库 | 建设和维护较重，当前需求与边际收益不明确 | 实际影响或使用频率上升，或出现低成本可复用工具时 |
| 为统一结构重构全部老项目、复制一套中央样板代码 | 会扩大范围、制造迁移与双份维护成本 | 有明确迁移目标，并能证明对该项目的持续收益相称时 |
| 每次任务全量加载、全量检查、完整日志与经验沉淀 | 普通任务反复支付上下文、执行与维护成本 | 特定任务的真实行为和风险确实需要相应检查或记录时，由模型按需选择 |

V3 的模型自主与客观边界保持现状，长期效果继续观察（observe）。效果案例、样板完善及其使用关系先小范围试验（experiment）。优先投入“已有明确痛点、可复用现有资产、可以小成本验证”的改进；高投入能力不因功能听起来完整就提前实施。

表中的补充与完善项同样适用有无能力的比较：若样板阅读、额外确认、检查或记录带来的总成本超过它节省的纠偏与返工，即使首轮交付率变高，也应缩小、暂缓或放弃该方案，而不是因已列入建议就继续添加。

这些取舍讨论系统能力建设，不降低当前任务的明确要求，也不以效率交换权限、用户已有改动、数据完整性或结果真实性。
