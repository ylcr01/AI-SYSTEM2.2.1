# V2.3.0 架构、使命与原则

## 系统使命

AI-SYSTEM 是面向个人开发者和强 Coding Agent 的轻量研发增强层，不替代模型、IDE、Agent Runtime 或项目自身工程体系。系统以真实研发问题和真实交付结果为反馈，在不实质降低模型理解、推理、探索、判断和创造能力的前提下，通过最小充分的 Context、Prompt、规则、Contract、Skill、工具和门禁，减少无效消耗与重复错误，使模型更高效、稳定地交付准确、高质量、优雅、清晰且可验证的结果。

系统是否成功不由规则、文件、Task、Evidence 或测试数量决定，而由真实用户目标是否被正确交付，以及为此付出的总成本决定。

## 六项核心诉求

| 核心诉求 | 本系统中的含义 | 不能用什么冒充 |
|---|---|---|
| 模型能力不降低 | 保留模型理解、推理、探索、方案比较、判断和创造空间；规则只约束可机器确认的事实与高风险边界 | 让模型机械服从更多步骤或加载更多背景 |
| 准确 | 正确理解用户目标、修改正确位置、覆盖关键行为、避免 Regression，并如实表达未知与未验证项 | 代码能运行、命令退出码为零或模型自评正确 |
| 高质量 | 结果完整、可靠、可维护、可验证，与项目架构和质量基线一致 | 文件更多、测试更多或流程更完整 |
| 高效率 | 缩短从用户目标到可接受结果的总时间与总成本，包括上下文、等待、验证、返工和控制面开销 | 只缩短首次编码时间，或把成本转移给用户和后续返工 |
| 优雅 | 使用与问题规模匹配的最小充分方案，职责清晰，不重复已有机制，不为假设中的未来提前扩建 | 抽象层更多、机制更复杂或统一所有场景 |
| 清晰 | 目标、Scope、代码、状态、验证边界、风险和交付表达都可理解、可追溯且不失真 | 长篇说明、完整日志或形式化状态名称 |

## 不可退化边界

- 不以效率提升交换准确性、用户已有改动、安全、权限、隐私、数据完整性或状态真实性。
- 不以流程完整交换真实交付结果，不以技术自检冒充用户验收或长期净收益。
- 不让过期文档覆盖当前代码、配置、Manifest、Git 状态和测试事实。
- 不为单次偶发问题向所有任务增加中央规则；项目特有问题优先在项目层解决。
- 简单任务保持简单；复杂、高风险、并发或需要持续交付状态的任务才承担对应控制成本。
- 任何中央机制，包括本使命与演进准入机制本身，都必须接受净收益评估和删除可能性。

## 问题驱动的演进闭环

```text
真实任务与用户结果
      ↓
记录问题、版本和证据
      ↓
分类：目标 / 上下文 / 实现 / 验证 / 控制面 / 验收 / 环境
      ↓
判断：偶发 / 项目级 / 中央重复问题 / 安全事件
      ↓
设计最小、可撤销的干预
      ↓
观察或受控试验
      ↓
keep / shrink / remove / observe / experiment
```

候选想法允许被记录，试验方案允许在限定范围内写入；只有真实证据表明至少一项核心诉求改善，且不可退化边界没有实质下降，才可宣称净正向并进入中央默认路径。完整准入规则见 [`55-系统演进准入.md`](55-系统演进准入.md)。

## 当前架构

系统由执行可信内核和按需工程质量内核组成。模型位于这些约束与事实之间，自主求解问题。

```text
项目事实 + Manifest + 最小质量参照
                ↓
          强模型自主求解
                ↓
       当前 ChangeSet 与 Evidence
                ↓
 Scope / Evidence / Review / 规格一致性 / 本地提交
```

执行可信内核只硬控确定性事实。工程质量内核通过 Quality Profile 路由 Contract 和 Canonical；Profile 是系统内部选择配置，不是宿主 Skill，也不规定模型思考过程。自动路由只在 structural 任务加载主要 Contract/Canonical，显式 `--quality-profile` 可为局部任务请求一个 Contract。详细规格追踪只在项目配置映射或明确声明规格影响时启用，Review Package 只在显式审查路径生成。项目可显式绑定外部整项目底座；底座只按任务相关性读取入口、质量清单、检查清单和最多两份资料，不复制源码。

系统知识的职责分开：本文件定义系统应追求什么；代码、配置、Manifest 和 Git 状态证明当前实际实现；真实任务、相关后续、返工和 Regression 证明机制产生了什么效果；Decision 解释为什么保留、修改或删除机制。说明文档只提供导航和已核验基线，不能替代任务相关源码分析。

V2.3.0 将内部 Task 状态压缩为四种默认用户状态，并把 Alignment、Change Rationale、Task Check、指纹和门禁细节留在 `--full` 宿主视图。Task Schema V10 只记录可由状态事件和精确 continuation 确认的结果事实，不保存用户消息正文，也不根据模型自评生成质量分数。

“本轮已交付”“完成轮次”“对话已收口”和“用户已验收”是不同事实：`waiting_acceptance` 对外映射为 `delivered`，表示工程结果已验证并形成本地提交，不要求形式确认；相关询问保持已交付，缺陷退回进入返工；范围扩展、非正式肯定或话题推进形成 `closed`；只有用户明确通过才能形成 `accepted`。后续分类只写入最小事实，不触发工程重验或自动创建新 Task。

`completion-rounds-v1` 从新版记录重新起算：一个问题只形成一个样本，完成轮次为首次有效交付加相关询问、缺陷返回或显式退回次数。没有后续的交付先保持观察，默认静默 7 天后计为一次完成；旧口径记录保留但退出分母。普通问答和纯只读分析不创建样本；仓库写任务自动标记 `problemType`，报告可按类型筛选。显式验收率只作为可选辅助事实，不再决定完成样本。
