# 重要设计点子与价值

记录日期：2026-09-07。来源：用户关于提高首轮交付准确性、满意度、效率及代码一致性的说明。

本文长期保存设计意图、解决的问题、已有基础和演进边界，避免以后只保留结构或规则，却忘记为什么建设。它是设计资料，不是自动加载、任务检查或实施授权；目标分析见[交付质量目标与发展建议](75-交付质量目标与发展建议.md)。

用户随后认可的最少协作约定、具体反馈解释和已实施范围见[模型自主研发执行方案](77-模型自主研发执行方案.md)，各点子不自动转成新增机制。

用户明确提出的点子：中央能力样板与项目模板、通过样板统一代码风格/文件结构/命名、提供其他可参考案例、按业务域组织代码。下面将这些点子分别展开，并把进一步建议注明为建议，避免混淆来源。

## 所有点子的共同目标与投入取舍

用户同日进一步明确：**最终目标是所有问题，一次就能高效率地完美解决。后续系统所有功能都围绕这个目标实现，高效率也是核心要求；某个场景要做得很重才能提升一点点，可以现阶段不做。** 权威目标见[架构与原则](10-架构与原则.md)。

因此，一个点子除了说明质量收益，还要观察它是否减少总耗时、沟通、返工和维护负担。样板、业务域、案例和反馈都用最小可用方式先解决真实问题；功能存在、资料完整或结构统一，本身不能证明值得投入。

比较基线是“不加该能力也能如何解决问题”。用户明确举例：不加能力，两轮对话、1 小时解决；加能力，一轮对话、2 小时解决，则不加。所有点子都按完成同一问题、达到同等合格结果后的总成本比较；不能因轮次减少就判定有收益，也不能单凭建设复杂或绝对耗时长就判定无收益。

| 点子 | 当前优先投入 | 当前不扩展到 |
| --- | --- | --- |
| 中央样板与模板分工 | 使用已有索引与真实源码，核对一个项目的适用关系 | 重复维护两份代码样板、自动选材平台 |
| 风格、结构与命名统一 | 完善代表性实现，复用项目已有格式工具 | 全部旧代码的批量改名和重构 |
| 业务域组织 | 完善实际目标领域的职责与关键事实 | 为目录一致建立微服务、完整 DDD 或迁移所有老项目 |
| 可参考案例 | 少量有区分度、可定位、说明原因的案例 | 覆盖所有长尾场景的庞大案例库 |
| 效果与行为参照 | 一个高频页面或流程的认可版本和关键结果 | 每次任务固定设计审批、截图归档和全状态矩阵 |
| 真实纠偏反馈 | 复用现有对话与 Git 做小批抽样 | 每任务中央账本、评分系统和长期仪表盘 |

暂缓重投入、微收益的方案是阶段策略，最终目标保持完整。后续根据实际需求、收益证据和成本变化再决定是否投入。

## 点子一：中央能力样板与项目模板分层协作

**来源：用户明确提出。当前状态：已有实现基础，使用效果待真实任务验证。**

### 核心想法

中央能力资料说明跨项目成立的职责、依赖和质量原则；工程模板用真实可维护的项目给出具体写法；业务项目记录自己的目标、规则与差异。模型有明确参照，同时保留针对当前问题选择最小方案的空间。

| 放在哪里 | 保存什么 | 例子 |
| --- | --- | --- |
| 中央能力区 | 通用职责、适用条件、质量取舍与样板说明 | 页面负责组装、完整业务流程有明确所有者、失败保留语义 |
| 工程模板库 | 框架与依赖、目录、命名、格式配置、可运行源码和具体样板索引 | Vue 的页面/弹窗/API 写法，芋道 Controller/Service/Mapper 链路 |
| 业务项目 | 领域术语、数据规则、接口事实、项目差异、认可的页面与局部样板 | 预约规则、权限来源、字段含义、实际操作反馈 |

### 为什么好、解决什么问题

- 通用经验可以复用，具体写法又有确定归属，减少模型每次重新设计同类结构。
- 模型可以从真实代码理解细节，降低抽象文字存在多种解释带来的输出波动。
- 框架变化主要由相应模板吸收，避免中央规则写满技术栈细节并影响无关项目。
- 具体源码在模板中保持一个维护位置，中央通过索引引用，减少两份代码样板长期漂移。

### 已有基础与下一步

中央已有能力 Contract 与样板，注册表已有 Web、App、Server 三个模板。Web 的 `docs/开发指南/新增业务模块.md` 已链接多类真实实现；服务端的 `.ai/10-指引/20-实现样板与模块边界.md` 已链接角色与品牌的完整链路。

下一步先验证一个真实项目是否能顺利找到适用模板与样板。已登记项目目前未绑定模板且本机路径不可用，不能把登记视为接入完成，也不应替老项目猜测绑定关系。

### 使用边界与收益观察

模板是一套工程基线，不是所有业务问题的答案。具体业务字段、权限、状态机不能照搬；全新项目可以明确选用模板，已有项目继续服从自身稳定约定，架构迁移单独考虑。

观察相似任务是否减少结构与接口写法纠偏，并同时观察读取、复制适配和模板维护成本。

## 点子二：用真实样板统一代码风格、文件结构和命名

**来源：用户明确说明样板的主要目的。当前状态：模板已部分实现，值得集中完善。**

### 核心想法

让模型看见“这个工程里合适的实现是什么样”，将格式与机械一致性交给已有项目工具，将职责、拆分和业务流程写法通过少量典型代码说明。

统一的范围包括目录和文件名、函数命名、API 与类型归属、组件输入输出、状态所有权、错误处理和格式。统一在同一项目与适用模板内成立；Web、App、Server 可以有各自适合的表达。

### 为什么好、解决什么问题

- 减少同一功能每轮生成不同目录、命名与抽象方式，降低用户纠正风格的沟通成本。
- 一致的结构让后续模型和开发者更容易定位修改位置，减少重复能力和错放文件。
- 真实代码能够展示细节取舍，例如何时保留一个文件、何时拆出纯模型、提交失败如何恢复。

### 已有基础与下一步

Web 模板已定义 `index.vue`、`data.ts`、`api/`、`components/`、`modules/` 等职责，也说明从最少文件开始。App 有 `use-*.ts` / `useXxx` 命名、页面局部状态和领域 Store 归属。服务端明确沿用既有 Controller/VO/Service/DO/Mapper。

下一步选择少量当前认可的普通与复杂实现，标明“参考结构”“参考交互”“参考错误处理”等具体维度。现存代码可以带有历史折中，不能因处于模板中就宣布每一处都是最佳实践。

### 使用边界与收益观察

不机械生成全部可选目录，不为目录整齐增加空层，不把所有文件强制拆小。既有项目若与模板不同，先确认项目现行约定；不要在功能任务中批量改名或格式化。

观察首次交付是否自然符合命名与职责预期，以及是否减少无关文件、重复封装和风格返工。

## 点子三：按业务域组织代码，让业务事实靠近实现

**来源：用户明确提出。当前状态：Web 与 App 已采用，服务端保留自己的模块与分层方式。**

### 核心想法

让一个业务能力的页面、接口、状态、规则和局部组件尽量相邻；领域说明解释其负责范围、术语、依赖与入口。模型从一个领域入口找到完成任务所需的大部分事实。

示意结构只表达责任，不要求所有目录出现：

```text
domains/
└─ reservation/
   ├─ DOMAIN.md      领域责任、术语与入口
   ├─ pages/         当前平台需要的页面
   ├─ api/           预约接口与契约
   ├─ components/    当前需要的局部组件
   └─ model.ts       存在独立纯规则时再创建
```

### 为什么好、解决什么问题

- 减少模型为了一个业务问题跨顶级页面、API、Store 目录搜集碎片，预期能降低上下文遗漏。
- 业务所有权明确，更容易判断应该改哪里、影响谁、哪些内容应留在本次范围之外。
- 相关内容一起演进，模型更容易发现接口、页面和状态之间的不一致。
- 共享能力有明确准入理由，降低把局部规则顺手提取到公共层后扩大影响面的概率。

### 已有基础与下一步

Web 使用 `app/domains/platform/shared`，App 使用 `app/domains/shared`，两者都有领域说明与依赖约定。服务端已有 System/Infra/BPM 模块和模块内技术分层，适合继续尊重其工程结构。

下一步在真实功能任务中观察定位耗时、遗漏和实际修改边界。领域文档只补职责、术语、公开入口和关键事实，不复制整份代码与接口说明。

### 使用边界与收益观察

按业务域组织不等于引入完整 DDD、微服务或每域独立 Package。领域划分不合理也会增加跨域跳转；简单功能不需要创建额外层次。老项目不因该点子成立而自动获得整体迁移理由。

观察模型能否更快找到完整调用链，以及局部功能是否减少跨域改动；不能只用目录数量评价收益。

## 点子四：保留其他可参考案例，并记录值得参考的原因

**来源：用户明确提出需要其他案例；以下记录方式为本次建议。当前状态：已有部分真实路径索引。**

### 核心想法

除了通用模板，再保留不同问题的代表性案例：普通 CRUD、树表、复杂联动、移动端恢复、权限分支、跨端联调、明确根因的局部修复。案例告诉模型在什么场景参考、参考哪一部分、为什么采用这种做法。

### 为什么好、解决什么问题

- 单一 CRUD 样板不能代表复杂配置或连续交互，案例可以补足适用场景。
- 记录取舍原因，可以防止模型只复制形式却遗漏真正要保持的行为。
- 经确认的“原问题—最终修改—验证结果”可以减少同类错误反复由用户纠正。

### 最小记录内容

| 内容 | 用途 |
| --- | --- |
| 场景与目标 | 判断是不是同类问题 |
| 实现路径与参考版本 | 能找到具体代码，避免引用漂移 |
| 值得参考的部分与原因 | 说明结构、行为或设计选择的价值 |
| 适用与不适用条件 | 避免照搬权限、接口和平台假设 |
| 实际验证与用户反馈 | 区分运行事实、技术通过与用户认可 |

这些内容可以写在已有索引的几句话中，不要求新 Schema 或每次生成案例文件。用户未明确认可时如实标注；临时截图、日志和完整对话不自动沉淀。

### 已有基础与下一步

先完善模板已有案例索引，挑选真正有区分度的内容。项目经验留在项目，模板共性留在模板；跨模板经验有独立证据后再提炼到中央。

观察是否减少重复错误与适配错误；案例太多、难以选择或长期失效时应删减索引，而非增加自动路由层。

## 点子五：将用户认可的效果和行为作为质量参照

**来源：针对“功能实现了但整体不满意”的本次建议。当前状态：有组件、主题与状态原则，建议小范围补充。**

### 核心想法

给代码样板配上用户可感知的成品参照，涵盖信息层级、密度、视觉比例、关键操作、状态衔接和错误恢复。模型交付前能把当前结果与具体预期对照。

### 为什么好、解决什么问题

- “优雅”“好看”“完整”存在解释空间，具体参照能减少模型与用户之间的预期偏差。
- 可以暴露构建与类型检查看不到的问题，例如表格整体过小、主操作不突出、失败后输入丢失。
- 将用户的一次认可转化成后续同类任务可用的偏好依据，减少重复解释。

### 最小落地与边界

从一个常用页面或流程开始，记录认可的版本、适用屏幕和数据、主操作、关键状态以及两三条取舍原因。必要时保存一张有明确参考用途的图；截图只能说明视觉，交互仍需实际行为验证。

这是质量参照，不建立每任务强制设计审批。不同产品和平台的体验目标可以不同，不能把一个页面的样式推广成所有系统的审美标准。

观察因布局、比例、交互与恢复问题产生的首轮退回是否减少，同时计入参考维护成本。

## 点子六：用真实纠偏决定补什么，让系统越用越准确

**来源：针对少沟通、少返工的本次建议。当前状态：有历史经验与评估口径，缺少可比较的 V3 结果样本。**

### 核心想法

从已经发生的用户纠偏中定位缺口：目标理解、事实不足、实现错误、效果偏差、工程风格、范围扩张或验证不足，再选择最靠近问题的修复位置。

### 为什么好、解决什么问题

- 避免把每次错误都解释成“缺一条中央规则”，控制系统复杂度。
- 让建设投入对应反复出现的真实损失，减少为假设场景预建能力。
- 把降低返工与用户等待作为结果，避免用文档、脚本、测试或流程数量自证进步。

### 最小落地与边界

优先修正当前项目的事实、代码或样板，很多失败无需形成新资料。工程判断主要保留用户明确认可的取舍与模型在真实任务中反复判断不好的地方，不大量重复通用常识；确认是模板共性再补模板，跨模板成立后才考虑中央经验。按需要抽样复盘现有对话和 Git，不恢复普通任务账本或状态机。

可以在近期同类任务中对照使用一个经过完善的样板，记录系统、模型、项目与模板版本。用户没有后续相关追问可以理解为暂时接受，不需要推断原因；以后再次出现相关问题继续记录，明确验收也不关闭问题。需要汇总时分列暂时接受、明确接受与后续问题，并说明观察范围；历史不可访问等情况注明观察不足。样本不足时只保留假设，不宣布首轮解决率提升。

观察收益时同时看准确性、整体满意度、范围、总耗时与维护负担；若投入持续增加而返工不下降，调整或停止该方案。

随着模型进步，已稳定掌握且不再有增益的补偿性经验可按事实精简或退役；仍有效的项目事实、接口契约和用户认可样板继续维护。暂时接受不自动证明某个案例值得作为标准，也不触发规则或 Skill 更新。

## 建议的下一次实践

选一个真实使用中的项目和一个高频功能类型，复用已选模板的现有实现，补齐样板适用条件、关键取舍与用户认可的效果参照，再观察下一批相似任务的首次交付。

这一步可以同时验证点子一至五是否提供有效信息，并通过点子六判断是否值得扩展。当前记录不自动触发模板修改、老项目迁移、仓库绑定或中央机制新增。
