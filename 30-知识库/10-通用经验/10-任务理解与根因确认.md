# 用需求与事实选择根因解释和修复方案

已有经验指出：把可见现象当成根因，容易围绕未经确认的解释继续实现。V3 后任务还暴露出另一种情况：相关事实已经读到，却没有用于取舍方案，随后测试也接受了错误预期。

## 怎样使用事实

把用户要改变的结果、已有且应保留的行为，与自己提出的解释分开。可疑代码只能支持候选原因；优先用当前输入、直接调用链或低成本复现区分解释，不要求所有现象由唯一机制解释，也不在证据不足时扩大确定性。

选择方案时，比较现有入口能否达到同一目标，以及新增机制实际解决了什么缺口。已有接口足够时，完整治理能力可以是另一项需求，不必随当前修复一起实现；现有机制确实不足时，允许必要的跨层修改，并说明依据。方案被用户同意，不替代模型对推荐成本的判断。

需要验证时，预期来自目标、已确认约定和故障条件，能够否定错误方案；不能仅证明新代码执行了自己设计的动作。相关实现存在多个直接入口时，核对同一业务含义在这些入口是否一致，不扩成全仓扫描。

## 验证结论要对应实际入口和处理环节

跨项目可迁移的判断是：验证有没有价值，取决于它能否触及本次错误发生的位置，而不取决于命令名称、退出码或测试数量。辅助函数行为、声明与类型、框架模板或宏转换、模块装载、运行交互和视觉效果是不同的证据范围。读取源码只是取得输入；将真实源码交给相应编译器，才覆盖该编译环节。测试替身若替换了本次修改的入口，也不能证明入口自身正确。

选择必要检查时，依据实际修改的文件和调用链，判断所选工具处理了哪些内容、是否保留故障条件。辅助函数单测与入口转换可以分别正确或失败；类型检查和构建是否覆盖同一环节，要看当前工具、配置和版本，不能按名称推断等价。缺口明确时优先复用已有检查或已安装的实际转换器，选择能辨别旧错误的最小验证，不默认叠加类型检查、构建和浏览器验证。结论表述也限定在实际覆盖范围内。

2026-09-14 PID Workbench 注释编辑案例：新组件的 7 处点击绑定直接包含单条 `if` 语句，当时安装的 Vue 模板编译器报表达式解析错误。首轮通过的 26 个单测未编译该新组件，当次 `vue-tsc` 也未报告这些错误；模型却将类型检查通过当成模板编译已覆盖。随后回归将真实组件送入 `compileScript(..., { inlineTemplate: true })`，修复前复现 7 处错误，修改事件绑定后通过。不能把这个案例外推为所有版本的类型检查都不能发现模板问题，也不能把框架模板当作任意 JavaScript 语句都可使用的位置。

根因归属已经核对：当次执行读取了中央入口和项目规则；中央已有必要验证与结果真实性要求，项目 `AGENTS.md` 更在 2026-09-11 的 `ce5b34c` 提交中明确要求确认检查是否真正覆盖修改入口。遗漏在模型对检查能力的选择和解释，没有将已读要求落实到模板转换环节；不是系统未接入，也不能归因于用户限制全仓或浏览器验证。当前系统不要求普通任务执行中央预检或固定生命周期，“走过流程”本身同样不能证明代码可用。

项目内保留框架回归，中央保留上述证据范围的判断。案例代码位于该项目 `apps/editor-web/src/views/pid/editor/components/canvas/RichAnnotationEditor.spec.ts`，当前还包含样式编译。故障复现与修复结果来自当次执行记录；本次整理核对了现存测试、配置和规则提交历史，未重跑历史检查，未把编译结果计作编辑器交互、可读性或视觉验收。

## 适用边界

这是按需参考的取舍样例，不是每任务必读清单。业务规则、协议和实现以目标项目为准，不复制案例中的字段或功能限制到其他项目。必要验证遵守当前根入口范围；简单修改无需输出方案对比、目标卡或额外审查报告。
